# Evaluation report

Three existing tool-using agents, run unchanged on new tasks, three trials each, with every step recorded
and checked. The tasks, answer keys, rubric code and run configurations were hashed before the first model
call (`eval/PREREGISTRATION.md`, `eval/frozen.json`); every change after that is in the change log at the end
of the pre-registration and in the section "Changes after the freeze" below. All tables are generated by
`python -m bench all` from the stored traces (`eval/results/summary.md`, `attribution.md`, `checks.md`,
`facts.md`), and every number in this report is checked against those files with evidence-check's script
(`tools/check_report.py`).

## Summary

- Tasks: 46 in all; ad review 20, business review 18, creator workflow 8.
- **Task success (pass^1) in the base run**: ad review 53/60 (88%), business review 47/54 (87%), creator
  workflow 21/24 (88%). pass^3, the chance that all three trials of a task succeed: 80%, 72% and 88%.
- **Base failed trials 17: caught by a gate 1, let through 16.** In ad review and the creator workflow every
  failure passed every gate: verbatim quotes, released numbers and passing skill scripts do not make a wrong
  decision right.
- **Needs human confirmation**: the business review's number check held 9/54 (17%) trials; 8 of the held
  trials were successes held for confirmation.
- **Process faults are common even when the answer is right**: in 36 of 60 ad review trials the agent also
  called submit_advice in a review turn, which its harness refused; ad review tool calls correct 351/387 (91%).
- **Where failures start**: of the 17 failed base trials, cause task (problems of the tasks or the answer
  key) 5; the rest are the agents' own (attribution table below).
- **Skills against no skills** (creator workflow): task success 21/24 (88%) against 8/24 (33%); per task,
  no-skills better on 0, worse on 6, same on 2, exact sign test p = 0.031.
- **Fixes, registered before they ran.** fix-ad: task success 54/60, trials with submit_advice called in a
  review turn 0/60, output tokens per trial 1,756 against 1,492 (-15%); every prediction held. fix-biz: store
  closures located at the merchant 6/6 (base 3/6) and task success 48/54 (base 47/54), with a side effect on
  B09; one prediction failed.
- **Total spend, all runs, the judge and the smoke test: US$1.48.**

## What was evaluated

| Family | Agent, as shipped | Tasks | Turns |
|---|---|---|---|
| Ad review | grounded-review, agent v1.3: reads the image (OCR), searches the policy library, checks its quotes with evidence-check, writes advice with a corrected version | Chinese ads under the Advertising Law and the SAMR guide, English ads under the TikTok ad policies; L1, L2, L3 | one, or three for L3 |

Model `claude-haiku-5-5`, effort medium, for every agent and the judge. In the base run, trial 1 went through
the standard API (latency measured) and trials 2 and 3 through the Message Batches API at half price. Answers
were fixed when the tasks were written, with the agent projects' own validators and builders.

## How it was scored

`rubric/RUBRIC.md` lists every check. In short:

- **Stages**, all rules over the trace: understanding (the request answered, within its stated constraints),
  planning (the steps the agent's own instructions require), tool calls (offered tool, schema-valid input,
  success), knowledge and citation (quotes verbatim with evidence-check's script, numbers backed by query rows,
  sources real and current), result quality (the answer key).
- **Task success uses the result checks only.** Process checks explain; they do not decide.
- **Gates** are the checks a deployment runs before release; a trial a gate holds needs human confirmation.
- **Attribution**: the earliest failing core check gives the stage; the cause comes from a rule per check or
  from a note written after reading the transcript (`eval/attribution_notes.yaml`).
- **Judged items**: what rules cannot check, judged twice per answer against a written guide.

## Gates and residual risk

A gate that never fires costs nothing and protects nothing; one that fires on every report costs a person.

- **Ad review** (quotes verified, decision consistent with the violations, corrected version complete): no
  trial held; the failures the gates let through are all of its failures. Every failed review cites real words
  and real clauses; it is the reading that is wrong.
- **Business review** (the number check): one of the failures the gates caught (B12, trial 3); the rest of the
  held trials were successes held for confirmation, each with one paragraph stating a number not in the rows
  it quoted.
- **Creator workflow** (the skills' checking scripts): no trial held; its failures are C06, where the scorer
  used as the answer key disagrees with the shipped script (see the attribution table).

So the gates mostly guard form (quotes, numbers, timing), and the remaining risk is judgement. In the business
review they also add review load: more correct reports held than failures caught.

## Process

- **Refused finishing calls.** In 36 of 60 ad review trials the agent called submit_advice in a review turn
  along with submit_review; the harness refused it and kept the review. The average length of those calls'
  input was 566 characters, output the agent wrote for nothing; it never failed a task (check T-4, report only).
- **Planning**: trials failing a planning check 3, of which in successful trials 3 (a skipped image read in the
  last turn, a skipped quote check, a last source check run on an empty card list).
- **Numbers on the first draft**: the business agent's report was released by the number check on its first
  draft in 15/54 (28%) of the trials (K-BZ-2), and after its one allowed rewrite in 45/54 (83%) (K-BZ-1).

## Fixes and the regression run

Both fixes were registered, with predictions, after base was scored and before they ran (pre-registration,
2026-11-18 20:48 +0800). Each is one addition to the agent's instructions, in general terms. Each ran on every
task of its family, three trials, Message Batches: that is the regression test. These are the tasks the
failures were seen on, so a gain shows the fix works on them, not that it generalises.

**fix-ad** adds two rules: one violation per phrase, under the most specific category; finish each request with
the one tool it asks for.

| Prediction | Base | fix-ad | Held |
|---|---|---|---|
| Failed trials with one phrase listed under two categories, at most 1/60 | 5/60 | 1/60 | yes |
| Trials with submit_advice called in a review turn, at most 6/60 | 36/60 | 0/60 | yes |
| Task success at least 53/60; no task that succeeded in 3 of 3 base trials fails in 2 or more | 53/60 | 54/60 | yes |
| Output tokens per trial at least 10% lower | 1,756 | 1,492 (-15%) | yes |
| zh-L3-03's rejected specification stays (not targeted) | failed | failed | yes |

Of the 5 base trials with one phrase under two categories, 4 failed because of it (en-L2-01 and zh-L2-01 in the
attribution table). fix-ad is adopted by the registered rule. Per task, fix-ad better on 2, worse on 2, same on
16; exact sign test p = 1.000: the gain is in the process, not in task success. Tool calls correct went from
351/387 (91%) to 345/345 (100%). Two new failures appeared: an extra GUARANTEE on a different phrase in en-L2-01,
and in zh-L3-02 a placeholder review (the model sent two submit_review calls in one message and the harness kept
the placeholder). The decision-consistency gate held that trial: with fix-ad, failures the gates caught 1.

**fix-biz** adds two rules to the business agent's prompt: locate a store-closure cause at the merchant; name only
slices the monitor flagged, or finer slices inside them, as causes.

| Prediction | Base | fix-biz | Held |
|---|---|---|---|
| Store closures located at the merchant, at least 5/6 | 3/6 | 6/6 | yes |
| Trials naming a cause on a slice the monitor did not flag for that lever: none | 1 (B07 trial 2) | 2 (B09 trial 3, B16 trial 1) | **no** |
| Task success at least 47/54; no task that succeeded in 3 of 3 base trials fails in 2 or more | 47/54 | 48/54 | yes |
| B02's extra cause on a flagged slice stays (not targeted) | failed | failed | yes |

fix-biz is adopted by the registered rule (it needs the first and third predictions), and the regression run
shows the cost of a rule written from a failure. Per task, fix-biz better on 3, worse on 2, same on 13; exact
sign test p = 1.000. B09 got worse: told to find the merchant behind store closures, the agent also narrowed a
refund rise spread across 深圳 × 茶饮咖啡 down to one chain (attribution table, run fix-biz). The second rule did
not stop causes on unflagged slices. pass^3 (all three trials succeed) went from 72% to 83%; the cost per trial
at the standard price went from $0.0109 to $0.0132. The next step is to move both rules from the prompt into code
(the lever decides the grain; a cause without an alert on its lever goes to a note) and re-run the refund tasks.

## Predictions against outcomes

The base predictions as registered in the pre-registration, and what happened:

- Ad review task success 75–95%, L1 ≥ L2 ≥ L3: held (base ad review success 88%, with L1 100%, L2 83%, L3 83%). The
  expected misses on en-L2-03, an ad that breaks a rule by leaving something out, did not happen.
- Business review weekly tasks 75–95%: held (base weekly requests 41/48). The scoped requests B17 and B18 were
  predicted to fail in at least half their trials and **did not** (scoped requests 6/6): prompt v4 kept to the
  question asked.
- Creator workflow with the skills 50–85%: **above the range** (base creator workflow success 88%).
- Tool-call correctness ≥ 95% in every family: **wrong for ad review** (tool calls correct 351/387 (91%)),
  because of the refused finishing calls.
- Needs human confirmation in ranges, with most failed trials caught by a gate: **wrong**. Base failed trials
  17: caught by a gate 1, let through 16.
- Planning failures in some successful trials: held (trials failing a planning check 3, of which in successful
  trials 3); planning pass rates lower than task success: **wrong**, they are higher.
- Cost per trial ≤ $0.01 for ad review and ≤ $0.02 for the others, whole evaluation ≤ $2: held (cost per trial
  as paid $0.0026, $0.0067, $0.0136; total spend US$1.48).
- Median latency 8–30 s, 30–120 s, 30–150 s: held (13.0 s, 47.4 s, 63.0 s).
- No skills ≤ 30% and base better by at least 30 points, better on at least 5 tasks and worse on none: base
  better by 54 points, on 6 tasks, worse on 0; no-skills success 33%, **just above** the registered ceiling.

The clearest miss is the gates: they were expected to catch most failures and caught one.

## Changes after the freeze

All in the pre-registration's change log, with times:

- One written verdict in the judge's calibration set was wrong and was corrected (agreement as written and after
  the correction, above).
- U-CR-3 searched the shot list's note to the creator as well as the video; it now reads the video only, as the
  rubric says. Task success does not change.
- Business review trials read a copy of their database; in the batch run, two trials of one case could not open
  the same file at once. The affected trials stopped before any model call and were run again.
- T-1 no longer counts a refused call of the other request's finishing tool; such calls count in T-2 (tool-call
  correctness) and in the new report check T-4. Task success does not change; the attribution of some failed
  trials does.

## Limitations

- Three trials per task over tasks written for this bench: intervals are wide (business review task success
  95% CI 76%–94%), and per-task comparisons rest on three trials each.
- The tasks are synthetic or fictional and come from the same project that runs them; two have a problem in the
  task or the key (C06, B02), kept in the scores.
- The judged items use the same model as the agents under evaluation, and the guide has a gap on quiet weeks; judged items do not change
  task success. No human ratings were collected.
- The fixes were checked on the tasks they were written for; new tasks are needed to show they generalise.
- Latency comes from the base standard-API trials, one per task; batch trials have no latency.

## Reproduce

```bash
python -m unittest discover -s tests   # offline
python -m bench all                    # offline: frozen hashes, re-score every stored trace, tables
python tools/check_report.py           # every number in this report against the result files
python -m bench run --config base --trials 1 --no-batch && python -m bench run --config base --trials 2-3
python -m bench run --config no-skills --trials 1-3
python -m bench run --config fix-ad --trials 1-3 && python -m bench run --config fix-biz --trials 1-3
python -m bench judge --calibration && python -m bench judge --run base
```
